# Cases and their methodological purpose

| Case | Domain | Best for | Key trap |
|---|---|---|---|
| [A — mode management](./A-mode-management.md) | Pilot–automation control | GDTA, mode-state, source, interface validation | selected ≠ active |
| [B — interrupted checklist](./B-procedure-interruption.md) | Flight-deck procedure | HTA plans, interruption, recovery, tests | checked ≠ achieved |
| [C — intermittent fault](./C-maintainer-fault-isolation.md) | Maintainer/diagnostics | ACTA, WDA, evidence uncertainty | self-test pass ≠ authoritative clearance |
| [D — team handoff](./D-team-information-handoff.md) | Distributed operation | team CTA, timing, data semantics | received ≠ understood/shared |

All statements are synthetic/fictional. They are constructed to support method practice and design inference, **not** to teach live flight or maintenance procedures. Real program application requires approved, authorized data and qualified operator review.

## Cross-case spiral
- Weeks 1–4 use A+B to teach ontology and work sequences.
- Weeks 5–8 use A+C to teach expert decisions and constraints.
- Weeks 9–12 use A+B+D to teach signal state, controls, procedures and coordination.
- Weeks 13–16 use all four to test construct validity, risk, transfer and standardized methods.

## Cross-case research question
Do the same analytical definitions work across flight crew, maintenance and teams without forcing distinctive work into a single task sequence? Document where field definitions require domain-specific extensions and which fields remain invariants.
