# Diagnostic answer key — model reasoning, not unique response

## Key principles
1. Mission outcome = operational result; function = capability/allocated transformation; task = actor's goal-directed work.
2. 'Green indicator' is a proposed UI solution, not an independently elicited need. Could be an allocated design requirement later if justified.
3. Task assess mode; decision remain or transition; need actual controlling state; control capability request and verify valid transition.
4. Action may serve different goals and often reflects environmental constraints; inference from button alone is unsound.
5. Receipt is transmission state; interpretation is human meaning; authority is justified belief about trustworthiness/source.
6. Normative procedure describes prescribed work; observation reveals work-as-done, possibly variation or workaround; neither should be silently overwritten.
7. Premature design primes user to justify offered concept and can occlude alternative strategies.
8. SME reports require context, provenance and engineering/safety review; requirements add verifiable allocation and rationale.
9. Examples: delayed activation, stale data, inhibited command, interrupted task, team handoff, contradictory indication.
10. Authority is a system/role constraint; visible button availability may not represent it accurately.
11. Hierarchy of goals/subgoals; plans specify conditional, ordered, repeated, parallel and stopping logic.
12. When operators must make consequential judgments based on variable cues, goals and future predictions.
13. Task diagram = high-level cognitive hot spots; knowledge audit = targeted tacit knowledge probes; simulation interview = situated unfolding judgments.
14. Recall is reconstructive and vulnerable to hindsight; logs/observation may support but not fully substitute for internal perceptions.
15. Constraints, means–ends, alternative strategies and adaptation to unexpected configurations.
16. Control task analysis; strategies analysis; social/organizational cooperation analysis; worker competencies analysis.
17. Example: bounded, stable low-risk UI change with good observable tasks and no relevant novel/adaptive conditions; document judgment and confidence.
18. Structural coverage and omission visibility, but cannot prove real-world completeness/validity.
19. Request → received → accepted/rejected → pending/executing → actual controlling/achieved → confirmed or recovered. States may vary by system; validate.
20. Correct selected-B field may falsely be interpreted as controlling-B; meaning and decision context matter.
21. Need describes what operator must know; provenance identifies which processed physical/logical source supports it with quality.
22. Example: *Under specified transition conditions, the system shall distinguish requested/selected from actual controlling mode.* Additional measurable criteria need evidence.
23. Primary outcome is correct actual procedure-related state, branch and recovery with independent ground truth, not clicks.
24. Correct state classification and recovery success; also wrong commands, actual primary task control, time with justified deadline.
25. Overt gaze is not comprehension; peripheral, strategic, missing data and inappropriate coding can confound interpretation.
26. Luminance, pupil-light reflex, anxiety, instrumentation, participant changes and fatigue.
27. Failure to reject does not bound difference within a meaningful equivalence margin.
28. Automation can reduce effort while increasing unrecognized errors or impairing monitoring.
29. Agreement = consistency across coders; validity = representation of actual work; utility = contribution to successful design/test decisions.
30. For example, deferred activation with concurrent workload causes incorrect selection/active judgments despite user preference for the concept.

## Mini-case high-scoring elements
A need linked to a real decision, accurate status distinctions, feedback with rejection/defer/recovery, implementation-independent requirement, two conceptually distinct designs, actual mode classification and inappropriate reliance/error as primary measures with independent simulator truth, and explicit warning that fixation on highlighted B does not prove understanding. Include assumptions/unknown acceptance thresholds.

## Scoring cautions
Alternative terminology or decompositions can be defensible. Penalize unsupported aviation-specific operating claims, ungrounded numerical thresholds and conflation of commanded versus actual system state more heavily than superficial formatting differences. Show uncertainty rather than fabricate facts.
